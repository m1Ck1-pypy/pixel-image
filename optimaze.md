## 1. Цели и ограничения

**Цели**

- Ц-1 (память, главная). Пик памяти на одну генерацию не должен превышать
  `~2 × исходник в RGBA` в дефолтном режиме и `~2 ×` в режиме вырезания фона.
- Ц-2 (латентность). 24 Мп → пиксель-арт: 564 → ≤ 250 мс; cutout: 386 → ≤ 250 мс.
  Дальше уже упираемся в однопоточное PNG-сжатие (`fdeflate`).
- Ц-3 (чистота). Убрать реаллокации и покадровые аллокации там, где это дешево.

**Ограничения (нарушение = откат этапа)**

- О-1. Результат побайтово не меняется. Для одинакового входа и параметров
  `_grid.png`/`_sprite.png`/`_cut.png` обязаны совпадать с текущими. Исключение
  только одно и явное: этап 6 меняет настройки компрессии PNG — там сверяем не
  байты файла, а пиксели после декодирования.
- О-2. Детерминизм не зависит от числа потоков. Один и тот же вход при
  `RAYON_NUM_THREADS=1` и `=16` даёт одинаковый результат.
- О-3. Бинарник GUI ≤ 10 МБ (запас под rayon и `png`).
- О-4. Поведение UI и контракт CLI не меняются (кроме размера cutout-превью,
  этап 2c — это осознанное изменение внешнего вида превью, но не результата).
- О-5. `crates/core` остаётся без побочек: не печатает, не знает про winit,
  не строит сетку для превью.
- О-6. Debug-сборка не должна разваливаться по `debug_assert` из-за новых
  чанковых проходов.

## 3. Инварианты, которые тесты обязаны защищать

1. Premultiplied alpha при уменьшении: цвет края не подмешивает фон.
2. Сетка рисуется только вокруг непрозрачных ячеек; прозрачная ячейка вдали от
   объекта остаётся `(0,0,0,0)`, а не цветом фона.
3. Палитра детерминирована: сортировка по ключу цвета, порядок HashMap не влияет.
4. `cut_faint_alpha` эквивалентен обнулению `0 < a < 16` до уменьшения.
5. `remove_background` не трогает замкнутые области меньше `min_hole`.
6. Исходник, переданный в конвейер, не мутируется (новый инвариант этапа 2b).

## 4. Правила одного этапа

Каждый этап — отдельный коммит (или 2–3 маленьких), и в нём:

1. Изменения кода.
2. **Тесты**, перечисленные в этапе; общий прогон
   `cargo test --workspace` и `cargo test --workspace --release`.
3. `pwsh -File scripts/bench.ps1 -Check` — без регрессий.
4. `pixel-image-gui.exe --dump-ui out\ui.png test.jpg` — сравнение с эталоном
   (для GUI-этапов). Дамп детерминирован: свой битмап-шрифт, фиксированный
   размер 1360×820, никаких системных метрик. Эталон этапа 0:
   размер `257 617` байт, SHA-256
   `F747B06086D7CE93C14FC270F11218577A68062E2D109464E94A664D5C558819`.
5. Строка «до/после» в таблице §6 этого файла.
6. Откат: `git revert` коммита этапа. Этапы 1, 2, 3, 5, 7 независимы; 4
   опирается на 1 и 3, 6 — на 1.

### Этап 2. Убрать лишние копии и лишнюю сетку (память, без rayon)

Три независимые подзадачи, можно тремя коммитами.

**2a. Превью не строит сетку**

- `crates/core/src/pipeline.rs`: `Conversion` больше не содержит `grid`.
  `convert_image(&RgbaImage, &Options)` возвращает `sprite` + `stats`;
  новая `render_grid(sprite: &RgbaImage, options: &Options) -> Result<RgbaImage>`
  — только для экспорта. `convert_file` вызывает обе.
- `crates/gui/src/worker.rs`: результат генерации — только спрайт (уже так),
  убрать ожидание поля `grid`.
- Экономия: `grid_w·cell × grid_h·cell × 4` — 11 МБ при `cell=16`, 45 МБ при
  `cell=32` на каждую генерацию в GUI.

**2b. Исходник не копируется**

- `convert_image` принимает `&RgbaImage`. Копия нужна только при
  `background_removal.is_some()` — тогда один рабочий буфер из
  `Scratch` (переиспользуется между генерациями, живёт в воркере).
- `cut_faint_alpha` переезжает в проход уменьшения: при премультиплае пиксель
  с `0 < a < 16` считается полностью прозрачным. Счётчик
  `faint_alpha_removed` считается отдельным дешёвым проходом по `&RgbaImage`
  без мутации (дополнительный проход только если нужен — при `--verbose`/статах
  всегда нужен, это O(N) по 1 байту, пренебрежимо на фоне ресайза).
- `crates/gui/src/worker.rs:316`: убрать `(**source).clone()`.
- Экономия: −4 байта/пиксель в дефолтном режиме (48 МБ на 12 Мп, 96 МБ на 24 Мп).

**2c. Cutout-превью**

- `crates/gui/src/worker.rs`: `DISPLAY_LIMIT` 4096 → 2048 (или от размера
  панели, если захочется). Экономия до 50 МБ на больших фото.
- Экспорт по-прежнему из файла в полном разрешении — контракт не меняется.

**Тесты**

- `pipeline::tests::convert_without_grid` — `convert_image` не возвращает сетку,
  `Stats.output_width/height` считаются по формуле `grid×cell`.
- `pipeline::tests::render_grid_matches_golden` — сетка, построенная отдельно,
  совпадает с эталоном попиксельно (инвариант 2).
- `pipeline::tests::source_not_mutated` — хеш `&RgbaImage` до и после
  `convert_image` (в том числе с `background_removal: Some(..)`).
- `pipeline::tests::borrowed_equals_owned` — старый путь (взять владение) и
  новый (`&`) дают одинаковые `_grid.png`/`_sprite.png` на всех фикстурах.
- `pipeline::tests::faint_alpha_inside_downscale` — фикстура с пикселями
  `a = 1..15` на краях: результат и `faint_alpha_removed` совпадают с прежними.
- `worker::tests::shrink_for_display_limits` (в `crates/gui/src/worker.rs`) —

- `alloc_budget` — пик байт для 256×256 падает (зафиксировать новое число).

**Критерий приёмки:** CLI 24 Мп pixel-art: commit 194 → ≤ 120 МБ; GUI на 24 Мп
(ручной замер): −96 МБ пика; результаты побайтово те же.

### Этап 3. Rayon: инфраструктура и «дешёвая» параллель

**Изменения**

- `Cargo.toml` (workspace): `rayon = "1"`; `crates/core/Cargo.toml`: зависимость.
  GUI и CLI напрямую rayon не используют.
- `crates/core/src/parallel.rs`:
  ```rust
  pub fn pool() -> &'static rayon::ThreadPool;      // один на процесс
  pub fn install<R: Send>(f: impl FnOnce() -> R + Send) -> R;
  ```
  Воркер и есть единственный потребитель (генерации сериализованы `mpsc`),
  поэтому глобальный пул безопасен. Число потоков:
  `available_parallelism()`, переопределение — `RAYON_NUM_THREADS`
  (1 = последовательный режим, нужен тестам).
- Параллелить:
  - `grid::upscale_with_grid` — по диапазонам `gy` (`par_chunks_mut` по строкам
    выхода), маска непрозрачности общая read-only;
  - `palette::histogram` — `fold` с локальным `HashMap` на поток, слияние,
    сортировка после слияния (инвариант 3);
  - `pipeline`: подсчёт прозрачных ячеек, ремап цветов;
  - `downscale::apply_alpha_threshold`, `clean::cut_faint_alpha`;
  - `pipeline::save_png` — композит/упаковка по строкам.
- **Не параллелить:** `remove_background` (DFS от границы), `remove_holes`,
  `despeckle` (маленькая сетка), PNG-сжатие (порядок IDAT).

**Тесты**

- `crates/core/tests/parity.rs` — общий помощник
  `assert_parity(serial_fn, parallel_fn)`, сравнение байт-в-байт:
  - `parity_grid`, `parity_histogram`, `parity_remap`, `parity_threshold`,
    `parity_save_png`;
  - каждый тест гоняет два пула: `ThreadPoolBuilder::new().num_threads(1)` и
    `num_threads(4)`, плюс дефолтный пул. Падение = недетерминированный участок.
- `parity::no_oversubscription` — `pool().current_num_threads() > 0` и пул
  создаётся один раз (проверка `ptr::eq(pool(), pool())`).
- `alloc_budget` — после параллелизации число аллокаций не растёт больше чем на
  число потоков (локальные аккумуляторы), пик байт не растёт.

**Критерий приёмки:** 24 Мп `--cutbg`: −20% времени (386 → ≤ 310 мс) или
зафиксированный в отчёте остаток «пол PNG-сжатия»; размер exe +≤ 0.3 МБ; все
`parity`-тесты зелёные в обоих режимах потоков.

**Риск:** средний. Главная ловушка — float-аккумуляторы (`weighted_variance`,
`weighted_average`) при параллельном суммировании дают другой порядок.
Их **не** параллелим или переводим на целочисленные суммы.

### Этап 4. Полосный (banded) downscale: память + rayon

Самый ценный и самый рискованный этап. Сначала убираем 4 байта/пикселя
(`pre 3 + al 1` на весь исходник), потом распараллеливаем уже полосы.

**Изменения**

- Новый модуль `crates/core/src/resize.rs`: разделимый ресэмплер
  `resize_premultiplied(src: &RgbaImage, gw, gh, filter) -> RgbaImage`.
  - Горизонтальный проход первым: промежуточный буфер `gw × h`
    (в premultiplied RGB + alpha). Для 24 Мп → 128×4000×4 ≈ 2 МБ вместо 96 МБ.
  - Вертикальный проход по промежуточному буферу → `gh` строк.
  - Полосы: горизонтальный проход — по диапазонам входных строк (каждая полоса
    пишет свои строки выхода), вертикальный — по диапазонам выходных строк.
    Общая память становится `O(gw · band)`, а не `O(w · h)`.
  - Ядра: Nearest, Box/Mode (остаются как сейчас, `downscale_blocks`),
    Triangle, CatmullRom, Gaussian, Lanczos3 — с теми же радиусом и
    нормализацией, что у `image::imageops::resize`.
- `Filter::downscale` переключается на новый модуль.
- Запасной вариант (решение по результату тестов паритета): если байтового
  совпадения для какого-то фильтра добиться не удаётся, оставить для него
  старый путь через `image` (флаг внутри `Filter::downscale`), а остальные
  перевести. Допуск на переходный период — не больше 1 LSB на канал.
- Спайк (2 часа, не коммитится): `fast_image_resize` как альтернатива —

## 7. Что сознательно не делаем

- **Не параллелим флуд-филл** (`remove_background`) — алгоритм последовательный,
  параллельная версия требует union-find и лишних массивов (то есть памяти),
  а время cutout и так падает на этапе 3 за счёт соседних этапов.
- **Не параллелим PNG-сжатие** — порядок IDAT фиксирован, `fdeflate`
  однопоточный. Это остаточный пол латентности.
- **Не включаем `-C target-cpu=native`** в распространяемой сборке: бинарник
  перестанет запускаться на старых CPU. При желании — `x86-64-v2` (AVX2),
  отдельным решением с проверкой на минимальной машине.
- **Не тащим `fast_image_resize`** без спайка: сначала свой полосный ресэмплер
  (этап 4), сравнение по трём критериям (паритет, время, память).
- **Не трогаем GPU-стек.** `pixels`/`wgpu` — это ~180 МБ базового WS; решается
  только переходом на `softbuffer`, это отдельный проект, не этот план.

## 8. Приложение А. Как воспроизвести замеры

```powershell
# 1. Инструменты (этап 0)
pwsh -File scripts/make-fixtures.ps1
pwsh -File scripts/bench.ps1 -Baseline

# 2. После этапа
pwsh -File scripts/bench.ps1 -Check

# 3. Время по этапам
.\target\release\pixel-image.exe out\bench\photo-24mp.jpg --verbose

# 4. Эталоны и тесты
cargo test --workspace
cargo test --workspace --release
$env:RAYON_NUM_THREADS="1"; cargo test --workspace

# 5. GUI-эталон
.\target\release\pixel-image-gui.exe --dump-ui out\ui.png test.jpg
```

Ручной замер памяти одного процесса (то, чем сняты числа §2):

```powershell
$exe = "target\release\pixel-image.exe"
$p = Start-Process $exe -ArgumentList "out\bench\photo-24mp.jpg" -PassThru
$ws = 0; $cm = 0
while (-not $p.HasExited) {
    $p.Refresh()
    $ws = [Math]::Max($ws, $p.PeakWorkingSet64)
    $cm = [Math]::Max($cm, $p.PeakPagedMemorySize64)
    Start-Sleep -Milliseconds 20
}
"WS {0:N1} MB, commit {1:N1} MB" -f ($ws/1MB), ($cm/1MB)
```

Для GUI пик читать так же, но на живой процесс; генерацию запускать вручную
(кнопка), после загрузки фото.
